# Design: Live Watch + Steer for In-Progress Agent Runs

Generated by /office-hours on 2026-09-27
Branch: main
Repo: yc-software/qm
Status: APPROVED
Mode: Builder

## Problem Statement

Today a QM agent's in-progress work is invisible unless you already have the exact
conversation tab open. There is no way to glance at "what is this run actually doing
right now" — for your own task, or for a teammate's — without either being the
original requester or waiting for the final reply. The user's framing: "what if we're
in an emergency, I want to launch the work quickly but I care what it's doing. Or, a
collaborator has launched some work, but I'm curious what it's up to. Visibility into
the work is optionality, I in 99% of cases may not choose to use it, but it's crazy
that the feature isn't there."

## What Makes This Cool

You kick off a task and walk away — or a teammate does, in a shared channel or
project — and either of you can pop open a live feed of exactly what the agent is
doing: which commands it's running, what it's reading and editing, in near real time.
99% of the time nobody looks. The 1% of the time someone does, it's because something
looks wrong, and they can just... type into the box and redirect it, mid-run, without
killing the task or losing the sandbox's accumulated state. And it turns out the
redirect half is nearly free — QM already has the plumbing for a shared-scope
participant to steer a run that isn't theirs; it's just never been exposed as a
dedicated "watch" surface.

It goes further than steering, too: the watcher can drop into an actual live terminal
inside the same sandbox the agent is using — type a command, hit enter, watch stdout
stream back — without waiting for the agent to decide to run it. That's the "emergency"
half of the original ask, and it turned out to be nearly free as well: QM already has a
background-process primitive (`startProcess`/`writeStdin`/`readProcess`) implemented
identically across every sandbox backend (local, E2B, Modal, Sprites, Smolmachines, AWS,
Porter, Superserve, agent37), already used in production for background jobs. A live
terminal pane is UI wrapped around a primitive that already exists everywhere.

## Constraints

Hackathon speed — build in a 2-3 hour window. Ship something demoable, not a full
subsystem.

## Premises

1. The core need is ambient optionality to look, not a takeover/control-transfer
   system. Full manual "drive the sandbox yourself" (VS Code Remote-style attach) is
   out of scope for this cut. — Agreed (user reframed away from initial "takeover"
   framing toward "visibility... 99% of cases may not choose to use it").
2. Steering a run that isn't yours is only free within shared scopes (channel,
   project) — `viewerMayUseRun` (`src/api/app-helpers.ts:235`) hard-blocks any
   non-owner viewer on DM/personal-scope runs. Watching/steering someone's personal
   task is a different, unbuilt feature (needs an explicit per-run grant) — deferred.
3. If we do nothing: teammates either wait silently for a shared-scope task to finish,
   or must already have that conversation's tab open to see live tool calls — there is
   no dedicated "what's running right now, that I'm allowed to see" surface.
4. Existing code to reuse, confirmed by reading the source: `getRun`,
   `getRunToolEntries`, `subscribeRun`, and `signalRun` in `src/api/app-turn.ts`
   already implement exactly this — live tool-call stream, activity log, and
   mid-run message injection — gated by `viewerMayUseRun`. The web UI
   (`plugins/web-ui/src/chat.ts`, `composer.ts`) already calls this API for the
   conversation you have open; it just isn't exposed as a way to find and open
   *someone else's* run.

## Approaches Considered

### Approach A: Watch mode + command escalation
Read-only live stream plus a new way to inject a raw command through the agent's own
`execute` path. Initially deprioritized as needing new tool-call-injection plumbing —
revised after finding `src/sandbox/exec-process-session.ts`'s `startProcess`/
`writeStdin`/`readProcess` primitive, which every sandbox backend already implements
identically. This is now in scope (see Recommended Approach, levels L2/L4).

### Approach B: Full live-session protocol (durable tape + driver handoff)
A first-class multiplexed live-tape protocol serving web, Slack, CLI, and a future
VS Code extension, with a real agent⇄human driver handoff state machine. Rejected for
this cut: genuinely new subsystem (concurrency, per-message secret ACLs, durable
driver state) — right architecture for a real roadmap, wrong size for a hackathon.

### Approach C: Spectator link, no control plane
Read-only "Watch" link next to Share, no steering at all in v1. Superseded once
premise 4 showed steering is already implemented for shared scopes — cutting it out
would throw away a nearly-free capability.

## Recommended Approach

**Watch + steer + live terminal, shared scopes only.** A graduated intervention scale,
all gated by the same existing `viewerMayUseRun` check (`src/api/app-helpers.ts:235`):

- **L0 Watch:** a "Live now" list of active runs the viewer is authorized to see (any
  run in a channel/project they're a current member of), and a Watch view that points
  the existing tool-call feed at someone else's `runId` instead of the viewer's own.
- **L1 Steer:** the existing composer, pointed at the watched `runId` — already works
  today via `signalRun`, no new code.
- **L2 Structured controls:** Abort / Approve-Deny / Edit-queued / Withdraw buttons in
  the Watch view, each a direct call to an already-existing signal
  (`signalRun` abort, `pendingApprovalForThread`, `editQueuedRun`, `withdrawRun`).
- **L4 Live terminal:** a terminal pane in the Watch view backed by the run's sandbox
  handle: `startProcess(handle, "bash")` on open, `writeStdin` per submitted line,
  `readProcess` polled (its `waitMs` long-poll is built in) to stream output back.
  Backend-agnostic by construction — every sandbox implements the same
  `ExecProcessSessions` interface. While a human terminal session is open on a run, the
  agent's own next `execute` call is held (simple mutual-exclusion lock on the run
  record) rather than solving real concurrent-writer semantics.

(L3 — one-shot command injection via a new signal kind — is subsumed by L4, which is a
strict superset for about the same effort.) L5 (real PTY fidelity) and L6 (VS Code
Remote-style attach, full driver-handoff concurrency) stay out of scope — see Open
Questions.

This is almost entirely a UI + one small locking primitive: `getRun`, `getRunToolEntries`,
`subscribeRun`, `signalRun`, and `startProcess`/`writeStdin`/`readProcess` already exist;
nothing new is needed in the sandbox or permission layer. DM/personal-scope runs stay
owner-only, unchanged, by the same existing check.

## Open Questions

- Personal/DM-scope watch (the true "emergency, I launched my own task and want to
  peek from another device" case) needs a new explicit per-run grant — out of scope
  for this cut, flagged as the natural v2.
- The agent-vs-human mutual-exclusion lock for L4 is a demo-grade simplification (block
  the agent's next `execute` while a human terminal session is open) — real concurrent-
  writer semantics (queueing, interleaving, conflict resolution) are deferred to a
  proper driver-handoff design if this graduates past a demo.
- VS Code / CLI attach was the original framing but was explicitly descoped by the
  user in favor of visibility-as-optionality; a `qm attach` CLI or VS Code extension
  would be a thin client over the same run + terminal API later, not new backend work.
  Real PTY fidelity (colors, `vim`/`less`, arrow-key history) would also be needed
  first — the current primitive captures stdout via shell redirection, not a true pty.
- Should "Live now" show ALL runs in scopes you're a member of, or just ones the
  current user hasn't seen the final reply to yet? Left for implementation judgment.

## Success Criteria

Demoable: open a second browser session as a different (shared-scope) user, kick off
a task from the first session, see it appear in "Live now" for the second user, open
it, watch live tool calls stream in, type a steering message and click Abort from the
second session, then reopen a fresh run and open its terminal pane, type a raw command,
and see real stdout stream back — all from a session that never issued the original
request.

## Next Steps

1. Add a "Live now" list surface (web UI): enumerate current shared scopes for the
   viewer, call `activeRunForThread` per scope, render as a list.
2. Add a Watch view: reuse `chat.ts`'s tool-call-feed rendering and `composer.ts`'s
   send path, parameterized by an arbitrary `runId` (today implicit as "the current
   thread's run") instead of always the viewer's own.
3. Wire `subscribeRun` for live push into the Watch view (same mechanism the owner's
   tab already uses).
4. Add L2 control buttons (Abort / Approve-Deny / Edit-queued / Withdraw) to the Watch
   view, each a direct call to its existing signal.
5. Add the L4 terminal pane: `startProcess` on open, `writeStdin` per line, poll
   `readProcess`; add the agent-execute mutual-exclusion lock while it's open.
6. Confirm `viewerMayUseRun`'s existing DM-vs-shared-scope split is enforced at every
   new call site added in steps 1-5 (it should be, since it's the same functions) —
   this is the one thing worth a deliberate check, not an assumption.
